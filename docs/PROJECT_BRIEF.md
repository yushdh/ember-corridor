你是这个项目的 Python 游戏开发负责人，同时负责动作设计、像素美术整合和运行验证。请与我长期开发一款原创 2D 横版动作 Roguelite 游戏。玩法体验参考《死亡细胞》的快速移动、近战节奏、翻滚闪避、关卡探索、武器构筑和死亡重开。

我的核心要求是：所有项目自编程序代码使用 Python；角色清晰可辨；像素动画完整；特效华丽且战斗信息清楚；项目能够分阶段持续增加内容。

请把下面内容作为长期项目规范，并按阶段实际实施。

### 一、项目边界与默认方案

1. 目标平台暂定 Windows 10/11、桌面单机、离线游玩、键盘为主。默认中文界面，字体必须实际支持中文。开发环境若不是 Windows，要区分当前环境验证与 Windows 验证。
2. 应用代码和资源处理工具全部使用 Python。允许使用 Python 库内部已有的原生实现与着色器；PNG、音频、字体、JSON、TOML 等属于资源或配置。
3. 不自行编写 C/C++、C#、JavaScript、GDScript 或 GLSL，不把项目改为网页游戏或其他语言引擎项目。
4. 默认采用 Python 3.12、Arcade、Pillow；测试按需采用 pytest，后期打包可采用 PyInstaller。先核对兼容性，再锁定实际安装和运行成功的稳定依赖版本。使用与该版本一致的官方文档，不混用不同大版本教程。
5. 首先验证窗口创建、图形能力、像素缩放和资源加载。Arcade 所需的图形能力不足时，说明具体原因与可行备选，再确定框架调整。确认框架后保持一致。
6. 允许 AI 生成和明确授权的图片、动画、音效与字体。默认采用不需要付费的资源；费用支出先问我。
7. 角色、世界观、地图、武器外形、界面、名称和音频采用原创或符合许可条件的素材，不能直接提取《死亡细胞》的资产。
8. 以下是长期目标，不要求在一轮内完成全部系统。每次只实施一个明确、可验收的阶段及其必要基础工作。

### 二、美术方向：首先保证正常游玩时看得清

1. 默认题材为“潮汐侵蚀的废弃铸造城”。主角是戴完整面甲的遗迹行者，雾蓝短披肩、黄铜护具、琥珀色武器能量；场景以低饱和深蓝、灰紫和青绿为主。这个设定可以后续调整，但同一阶段保持一致。
2. 主角与敌人必须具有可辨认的头部、躯干、四肢、装备和朝向。调试方块、火柴人、圆点只能作为明确标记的临时占位，不能通过最终角色验收。
3. 建议逻辑画布 640×360，默认窗口 1280×720，支持 1920×1080。游戏世界采用最近邻、整数倍缩放；非整数窗口尺寸采用留边，保持比例，避免模糊与像素尺寸不一致。
4. 主角基础帧建议使用 96×96 透明画布，身体实际高度约 56–64 像素，宽约 28–40 像素。以图像左上角为原点时，基础脚底锚点可设为 (48,80)。
5. 大刀光、爆炸和技能独立成层，不通过缩小人物来塞进特效。个别动作需要更大画布时，明确记录锚点偏移。
6. 物理位置保留浮点数，最终绘制时统一处理人物与镜头的像素对齐。身体碰撞盒、受伤框、攻击框和图片画布分别定义。
7. 背景降低细节密度与饱和度，主角保留清晰轮廓。至少区分远景、中景、可碰撞地形和少量前景；装饰前景不能遮住关键战斗信息。
8. 使用正常镜头距离检查人物清晰度，不以放大的角色单图代替游戏画面验收。

### 三、角色动画与素材管线

1. 最迟在首个完整关卡中完成：待机、奔跑、起跳、下落、落地、翻滚、三段轻攻击、重武器攻击、受击、死亡。
2. 制作起点建议：待机 6 帧、奔跑 8 帧、起跳和下落各 2–3 帧、落地 3 帧、翻滚 6–8 帧、每段轻攻击 6–8 帧、受击 3 帧、死亡 8 帧。优先保证关键姿势与时序，不能复制同一帧凑数量。
3. 不同动作必须有真实姿态变化。不能仅平移、旋转或晃动一张静态图，便宣布完成逐帧动画。
4. 动画数据至少包含帧路径或图集区域、每帧时长、锚点、必要的武器挂点和事件。攻击前摇、伤害有效段、后摇与可取消窗口必须明确。
5. 换帧时保持统一的角色基准锚点、尺度、服装和武器，避免非动作设计导致的整体漂移；允许脚部因奔跑、跳跃、翻滚自然改变位置。左右翻转时，同步处理武器挂点和判定框。
6. AI 生成的精灵表先视为待处理原料。必须检查真透明通道、帧数、切片尺寸、肢体与服装一致性、武器形状、像素尺度和锚点；处理后实际播放检查。
7. 为每份资源记录文件路径、用途、来源、作者或生成方式、许可依据、署名要求和处理步骤。不要凭“免费可下载”推定可任意使用，也不要随意把 AI 生成素材标成 CC0。
8. 先检查你当前是否具备绘图、下载和资源处理能力。没有绘图工具时，可接入合适的授权素材；若仍缺关键素材，列出准确规格和绘图提示词，并完成其他可推进的工作。
9. 资源必须真实存在且能加载。缺失素材、占位素材和未完成动画必须显式记录，不能用不存在的路径或无提示的方块替代来掩盖。
10. 程序生成美术也可以采用，但同样必须通过角色清晰度、风格一致性与动画质量验收。

### 四、移动、战斗与操作

1. 默认键位：A/D 移动，Space 跳跃，J 攻击，K 翻滚，Q 技能，E 交互，1/2 切换已持有武器，Esc 暂停。单向平台可采用 S+Space 下穿。后续提供键位设置。
2. 移动应响应及时，有合理的起步、停止和空中控制；实现按键时长影响跳跃高度、跳跃输入缓冲和离地宽容时间。后两项先以约 0.1 秒为调参起点。
3. 明确地面、墙面、头顶、平台边缘和单向平台碰撞。角色高速移动或翻滚时也不能穿过实体墙。
4. 采用固定步长更新核心逻辑，初值可为 1/120 秒；渲染独立，追帧次数设上限。统一速度、加速度和计时单位，避免动作速度绑定渲染帧率。
5. 轻武器实现三段连击与输入缓冲；重武器体现更长准备、更强冲击和不同风险。不要只改攻击颜色与伤害数字。
6. 翻滚具有明确的持续时间、冷却、方向、无敌窗口及取消规则。死亡、重开和暂停后不能遗留无敌状态。
7. 伤害由有效攻击事件触发，并按攻击实例做命中去重。普通单段攻击不能因覆盖敌人多帧而重复扣血；明确设计的多段攻击按各段规则结算。
8. 明确攻击、受击、翻滚与死亡之间的中断规则。动画、可见武器范围与实际判定一致；武器能否穿越地形由明确规则决定。
9. 首个完整关卡包含三种行为不同的普通敌人，例如近战追击、远程蓄力和重甲冲击。敌人具备清晰的准备动作、有效攻击与恢复窗口。
10. Boss 具有可学习的招式与阶段变化，使用动作、音效和危险区域提示攻击。不能仅靠巨大血量或无预警伤害增加难度。
11. 持续通过实际游玩调整手感。自动测试通过不能代替对输入响应、动作衔接和战斗节奏的检查。

### 五、华丽特效与打击反馈

1. 基础效果包括逐帧刀光、角色残影、命中闪光、方向性火花、少量碎屑、落地尘、局部光晕、镜头震动和短暂打击停顿。
2. 优先用已有库功能、预制透明贴图、粒子精灵和叠加混合完成效果。不要把自行编写着色器作为首版的前置条件。
3. 轻击停顿可从 30–50 毫秒、重击从 60–90 毫秒开始调试；普通震动可从 1–3 个逻辑像素、持续 80–160 毫秒开始。所有数值集中配置，并以实际体验修正。
4. 普攻、重击和技能有不同的节奏、形状、颜色和音效强度。爆发力来自清楚的动作与层次，不靠持续覆盖整个屏幕。
5. 敌人预警、主角轮廓和危险区域必须在强特效下仍可辨认。预警不能只依靠一种颜色。
6. 打击停顿不能阻塞系统事件处理；输入采集、界面和音频时钟分别处理，防止卡键、声音中断与暂停异常。
7. 提供震动强度、闪光强度、音量和特效质量设置。粒子、残影、光晕有并发上限和回收机制。
8. 音效覆盖挥空、命中、受击、翻滚、落地与关键敌人预警；控制叠音数量和整体音量。

### 六、长期玩法与首个完整目标

1. 长期循环：进入区域 → 战斗与探索 → 获得武器或能力选择 → 挑战 Boss → 进入新区域或结束本局 → 保留明确的永久解锁。
2. 首个质量基准版本只包含一个原创区域、4–6 个手工连接房间、两类武器、一个主动技能、三种普通敌人和一个 Boss。
3. 该版本需具备开始、暂停、死亡重开、胜利结算和操作提示，目标体验长度约 5–10 分钟，以实际游玩为准。
4. 先证明手工关卡好玩，再增加装备掉落、局内构筑、局外解锁和存档。
5. 随机化从经过验证的房间模板开始。检查房间图连通，也检查角色跳跃能力、实际碰撞空间、入口出口和必要目标可达性。
6. 保存随机种子，失败布局重试或使用可靠备用布局。批量检查若干种子只能证明已检查样本，不得宣称所有布局均获证明。
7. 游戏逻辑随机数与装饰特效随机数分开，避免调画质或粒子数量影响掉落与关卡。
8. 新武器、敌人、关卡与 Boss 分批增加，每批引入明确的玩法差异，并符合已有质量基准。

### 七、工程与性能

1. 按实际需要划分场景、输入、角色、动画、战斗、敌人、关卡、特效、音频、界面、资源和存档模块。保持职责清楚，避免单文件堆满全部系统，也避免提前搭建通用引擎。
2. 武器数值、敌人参数、动画与房间配置适度数据化；复用真实需求，不建立无实际用途的配置语言或复杂插件系统。
3. 资源路径按项目位置解析，不依赖当前工作目录；运行入口统一，例如 python -m game。
4. 资源预加载、精灵分层批量绘制；静态地形使用适当空间索引。不要在战斗主循环重复读文件、创建大图或做全屏 Python 逐像素运算。
5. 目标是目标电脑上接近稳定 60 FPS 的体验。这是待验证指标，不是默认已达成的事实。
6. 从首个完整关卡开始保留可重复的高负载战斗场景，记录硬件、依赖版本、窗口与逻辑分辨率、画质、敌人与粒子数量、平均帧率和 P95/P99 帧耗时。
7. 重复死亡、重开和切换场景后检查对象、事件订阅、音效实例与内存是否持续累积。
8. 存档采用可验证的数据结构，包含版本号、原子写入与必要备份；局内状态和永久解锁分开。读取损坏存档时说明情况，不能静默覆盖唯一有效存档。
9. 只为重要规则建立有意义的测试，优先验证攻击命中去重、翻滚无敌边界、关键碰撞、死亡中断、不同渲染频率下的动作一致性，以及后期的存档和地图可达性。
10. 发行包必须在目标操作系统实际验证启动、资源加载、输入、音频、存档和退出；未验证时明确标注。

### 八、八个开发阶段及验收

**阶段 1：可运行工程与美术样板。**

建立依赖、入口、资源加载、逻辑画布和输入；完成一个小型场景、真实主角造型及待机和奔跑动画。

验收：能启动、能左右移动，角色正常距离可辨，缩放清楚，资源能加载，有实际运行截图。

**阶段 2：移动与碰撞。**

完成跳跃、落地、单向平台、翻滚、镜头、输入缓冲与离地宽容。

验收：平台边缘、墙角、头顶和高速移动有效；动作不会随渲染帧率明显变化。

**阶段 3：战斗核心。**

逐个完成轻武器、重武器、三种普通敌人、伤害、受击、无敌窗口和基础反馈。

验收：动画与伤害同步、命中不重复、敌人预警清楚、战斗状态可正常中断。

**阶段 4：首个完整成品关卡。**

整合手工关卡、主动技能、Boss、完整角色动作、正式场景、音效特效和首尾流程。

验收：可以从开始玩到结算；核心人物美术无未说明占位；真实战斗画面、动画和运行结果达到质量基准。

**阶段 5：装备、构筑与存档。**

增加有限数量的掉落、装备选择、升级、永久解锁和设置保存。

验收：拾取、装备、效果、死亡重置、永久保留构成完整循环；损坏存档处理明确。

**阶段 6：受约束的关卡随机化。**

使用已验证房间模板、独立随机种子和可达性检查。

验收：指定种子可复现，主路径与必要目标可完成，失败布局有可用兜底。

**阶段 7：分批扩展内容。**

每批聚焦一个新区域或少量有玩法差异的武器、敌人和 Boss。

验收：新增内容达到阶段 4 标准，既有战斗、画面与存档无明显退化。

**阶段 8：集中优化与发行准备。**

依据测量优化、调平衡、完善设置与教学、整理来源说明并打包。

验收：目标平台实际运行和核心流程通过，性能记录真实，已知问题透明。
